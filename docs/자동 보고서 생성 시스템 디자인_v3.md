
# 자동 보고서 초안 생성 시스템 설계 문서 (V3)
Version: 3.0  
목적: 코드/스키마/API/의존성/실행환경 변화를 분석하여 **자동으로 보고서 초안을 생성하고 사람이 5분 이내 수정하여 제출 가능한 수준**까지 만드는 시스템의 구현 설계

---

# 1. 문서 목적

이 문서는 다음 목표를 만족하는 **실제 구현 가능한 수준의 설계**를 제공한다.

- commit message 품질에 의존하지 않음
- 로그가 없어도 동작
- Git 밖에 있는 배포본/서버 상태도 일부 반영
- 하나의 프로젝트가 여러 repository로 분산되어 있어도 대응
- 민감정보를 저장하지 않음
- 보고서 생성 시점에만 동작 가능
- 완전 자동이 아니라 **자동 초안 + 사람 5분 수정**을 목표로 함

# 3. 전체 목표 구조

전체 흐름

```text
보고서 생성 요청
  ↓
대상 서비스 선택
  ↓
관련 repository / runtime / DB / API / dependency 증거 수집
  ↓
diff 정규화
  ↓
noise filtering
  ↓
change event 생성
  ↓
change correlation
  ↓
보고서 초안 생성
  ↓
LLM 요약(선택)
  ↓
사람이 3~5분 내 문장 보정
  ↓
최종 제출
```

핵심 원칙

```text
원천 데이터 = 증거(Evidence)
중간 결과 = 변경 이벤트(Change Event)
최종 산출물 = 보고서 초안(Draft)
```

# 8. Multi-Repository 대응 설계

## 8.1 왜 필요한가

하나의 기능 변경이 여러 repo에 동시에 걸쳐 있을 수 있다.

예

- api-server: endpoint 추가
- admin-server: 관리자 화면 대응
- common-lib: 공통 정렬 유틸 추가
- batch-worker: 후처리 배치 수정

즉 repo 단위가 아니라 **기능 단위로 묶어야** 보고서 품질이 올라간다.

## 8.2 핵심 원칙

- 분석은 repo별로 수행
- 결과는 project 단위로 병합
- 최종 보고서는 project 단위 change event 중심으로 생성

## 8.3 병합 기준

- 동일 엔티티/테이블명
- 동일 endpoint prefix
- 동일 기능 키워드
- 동일 시점에 변경된 공통 모듈 연계
- 동일 config key namespace

### 목적

- artifact hash
- jar hash
- config fingerprint
- 활성 endpoint 목록(선택)

### 보안 원칙

- 값 자체 저장 금지
- hash 또는 key 목록만 저장

### 한계

- 과거 snapshot이 없으면 과거 runtime 비교는 제한적
- 초기 도입 시 baseline 부재 문제 존재

# 10. Evidence 정규화 규칙

Analyzer별 출력 형식이 달라지면 후속 처리 비용이 커진다.  
따라서 모든 Analyzer 결과를 공통 DTO로 정규화한다.

예시

```json
{
  "sourceType": "GIT",
  "sourceName": "api-server",
  "targetPath": "src/main/java/.../BookRepository.java",
  "changeType": "FILE_MODIFIED",
  "metadata": {
    "layer": "REPOSITORY",
    "keywords": ["book", "sort", "query"]
  }
}
```

공통 필드

- sourceType
- sourceName
- targetPath
- changeType
- metadata
- confidenceScore

# 11. Noise Filtering 규칙 세트

## 11.1 목적

의미 없는 변경을 제거하여 보고서 품질을 높임

## 11.2 대표 노이즈

- import 정리
- formatting 변경
- 주석 수정
- logger 메시지 수정
- 테스트 코드 변경만 존재
- README 수정
- build timestamp 차이
- generated file 차이

## 11.3 규칙 예시

```text
if only import change → ignore
if only comment change → ignore
if file path contains /test/ and no production change → ignore
if metadata indicates formatting-only → ignore
if generated file hash changed but source stable → low priority
```

## 11.4 필터 결과 분류

- DROP: 완전 제거
- DOWNGRADE: 중요도 낮춤
- KEEP: 유지

# 13. Change Correlation 설계

## 13.1 왜 필요한가

동일 기능이 여러 증거에서 중복 탐지되기 때문

예

- schema diff: sort_order 추가
- repository diff: BookRepository 변경
- api diff: /books/sort 추가

이 세 개를 각각 보고서에 쓰면 중복이다.  
따라서 하나의 change event로 묶어야 한다.

## 13.2 correlation key 후보

- entity/table name
- endpoint prefix
- domain keyword
- shared config namespace
- 동일 repo group
- 동일 시점 window

## 13.3 처리 방식

```text
if evidence set share same domain keyword + adjacent timestamps + linked layers
→ same correlation group
```

## 13.4 주의사항

너무 공격적으로 묶으면 다른 기능이 하나로 합쳐지고  
너무 보수적으로 묶으면 동일 기능이 여러 줄로 분산된다.

초기에는 **보수적으로 묶고 사람이 합치는 방식**이 안전하다.

# 15. Draft Generator 설계

## 15.1 출력 원칙

```text

```

## 15.3 Markdown 출력 예시

```markdown
# 작업 보고서 초안

## 1. 작업 개요

## 2. 주요 변경 사항
1. 도서 정렬 기능 추가
   - manual_book 테이블에 sort_order 컬럼이 추가되었습니다.
   - 도서 조회 로직이 정렬 기준을 반영하도록 수정되었습니다.

2. 도서 목록 조회 쿼리 개선
   - 정렬 및 조건 처리 로직이 개선되었습니다.

3. 공통 모듈 업데이트
   - 참조 중인 common-lib 산출물이 변경되었습니다.
```

# 18. 구현 시 주의사항

## 18.1 commit message를 다시 믿으려고 하지 말 것

초기 품질이 낮더라도 evidence 기반 구조를 유지해야 한다.

## 18.2 raw diff를 바로 보고서로 쓰지 말 것

보고서는 diff 목록이 아니라 기능 단위 문서여야 한다.

## 18.3 처음부터 100% 자동화를 목표로 하지 말 것

초안 품질 70~80점 + 5분 수정 가능 수준이 목표다.

## 18.4 runtime snapshot 범위를 과도하게 넓히지 말 것

초기에는 다음만 권장

- artifact hash
- dependency fingerprint
- config key set
- endpoint snapshot

## 18.5 rule engine을 코드에 하드코딩만 하지 말 것

운영 중 변경 가능하도록 DB 또는 설정 기반 룰 구조 필요

# 20. 성능 및 캐시 전략

## 20.1 기본 원칙

보고서 생성은 요청 시 수행하지만, 반복 요청이 많으면 일부 캐시 가능

## 20.2 캐시 가능 항목

- repository mapping
- 최근 분석 기준의 endpoint snapshot
- dependency fingerprint
- schema metadata

## 20.3 캐시 금지 또는 신중 항목

- 최종 draft 본문
- change event 확정 결과

## 20.4 대형 repo 대응

- file path pre-filter
- layer별 대상 파일만 분석
- 병렬 repo 분석
- timeout 및 partial result 허용

# 21. 100+ Repository 환경 운영 전략

## 21.1 문제

repo 수가 많아지면 모든 repo를 항상 분석하는 것은 비효율적이다.

## 21.2 해결 전략

### 전략 A: 프로젝트-레포 매핑 정확화
서비스와 무관한 repo는 제외

### 전략 B: priority repository 지정
핵심 repo 먼저 분석

### 전략 C: changed repository only
base/target 기준 변경 없는 repo는 스킵

### 전략 D: 공통 모듈 영향 별도 처리
common-lib 변경 시 영향 후보 프로젝트만 마킹

### 전략 E: partial analysis 허용
시간 초과 시 "추가 확인 필요" 섹션에 기록

# 25. 구현 성공 기준

다음 기준을 만족하면 성공으로 본다.

- 사람이 5분 이내 수정 가능
- 보고서 누락률이 수동 작성 대비 낮음
- 보안 민감정보 저장 없음
- multi-repo 프로젝트 대응 가능
- false positive가 운영 가능한 수준
- raw diff를 직접 읽지 않아도 초안 이해 가능

# 26. 최종 결론

이 시스템은 **완전 자동 보고서 생성기**가 아니라  
**근거 기반 자동 초안 생성기**로 설계해야 한다.

핵심은 다음 세 가지다.

```text
1. Evidence 수집
2. Change Event 변환
3. 사람 5분 수정 가능한 Draft 생성
```

특히 품질의 대부분은 아래에서 결정된다.

```text
diff → change event 변환 엔진
```

즉, 좋은 시스템은
"코드 차이"를 많이 보여주는 시스템이 아니라
"사람이 바로 제출 가능한 설명 초안"을 잘 만드는 시스템이다.
