
# Auto Report Draft System – Spring Boot 구현 로드맵 (V3 기반)

목표:
V3 설계 문서를 기반으로 **자동 보고서 초안 생성 시스템**을 Spring Boot 프로젝트에 단계적으로 구현한다.
각 단계는 **구현 → 테스트 → 다음 단계** 방식으로 진행한다.

핵심 원칙
- 작은 단위로 구현
- 각 단계마다 테스트 수행
- 변경 이벤트(Change Event) 중심 설계 유지
- 보안 정책 준수 (민감 정보 저장 금지)

---

# 1단계: 프로젝트 기본 구조 생성 ✅

목표:
Spring Boot 프로젝트 기본 구조를 만들고 핵심 패키지를 생성한다.

베이스 패키지: `io.github.gloryoutput.docsgenerator`

패키지 구조

```
io.github.gloryoutput.docsgenerator
├─ analyzer/
│  ├─ git/          # Git diff 분석
│  ├─ api/
│  ├─ database/
│  ├─ dependency/
│  └─ runtime/
├─ common/          # BaseEntity 등 공통
├─ config/          # 설정 (H2Console, WebConfig, EnvFileLoader)
├─ controller/      # REST Controller
├─ domain/
│  ├─ analysis/     # 분석 요청
│  ├─ project/      # 프로젝트, 프로젝트 코드
│  ├─ repositorymap/ # 레포 매핑, 인증 정보
│  ├─ evidence/
│  ├─ changeevent/
│  ├─ report/
│  └─ ruleset/
├─ dto/
│  ├─ request/
│  └─ response/
├─ enums/
├─ exception/       # GlobalExceptionHandler
├─ service/
└─ util/            # EncryptionUtil
```

필요 의존성

- spring-boot-starter-webmvc (Spring Boot 4.0.3)
- spring-boot-starter-data-jpa
- springdoc-openapi-starter-webmvc-ui
- lombok
- mysql-connector-j
- h2 (개발용)
- jgit
- poi-ooxml

엔티티 기본 공통 필드 (BaseEntity)

- createdAt
- updatedAt
- isDeleted
- deletedAt

DB 컨벤션

- PK: `id_테이블명`, binary(16) (UUID)
- FK: `id_참조테이블명`, binary(16)

환경 설정

- dev 프로필: H2 인메모리, ddl-auto: create-drop
- local 프로필: MySQL 127.0.0.1:3307/reportdb, ddl-auto: update
- prod 프로필: MySQL, 환경변수 사용, ddl-auto: validate
- 환경별 `.env` 파일: `deploy/.env.dev`, `deploy/.env.local`, `deploy/.env.prod`

# 3단계: Analysis Request + Git Analyzer 구현 ✅

목표:
project_code와 기간을 전달하여 등록된 모든 레포지토리의 Git 변경 데이터를 수집

테이블: analysis_request

| 컬럼 | 타입 | 설명 |
|------|------|------|
| id_analysis_request | binary(16), PK | 분석 요청 ID |
| id_project | binary(16), FK | 프로젝트 참조 |
| requested_by | varchar | 요청자 (선택) |
| start_date | date | 분석 시작일 |
| end_date | date | 분석 종료일 |
| status | varchar(20) | 상태 (PENDING → RUNNING → COMPLETED/FAILED) |
| started_at | datetime | 분석 시작 시각 |
| completed_at | datetime | 분석 완료 시각 |

API 엔드포인트

| Method | URL | 설명 |
|--------|-----|------|
| POST | /api/analysis | 분석 요청 (project_code + 기간) |

요청 예시

```json
{
  "projectCode": "FOOTBALL",
  "startDate": "2024-01-01",
  "endDate": "2026-03-10",
  "requestedBy": "test"
}
```

응답 구조

```json
{
  "success": true,
  "data": {
    "idAnalysisRequest": "...",
    "projectCode": "FOOTBALL",
    "startDate": "2024-01-01",
    "endDate": "2026-03-10",
    "status": "COMPLETED",
    "repositoryResults": [
      {
        "repositoryName": "football_web",
        "totalCommits": 5,
        "commits": [
          { "commitHash": "...", "authorName": "...", "message": "...", "dateTime": "..." }
        ],
        "fileChanges": [
          { "changeType": "MODIFY", "filePath": "src/..." }
        ],
        "error": null
      }
    ]
  }
}
```

Git Analyzer 동작

- JGit으로 레포지토리 클론
- target_branch 기준으로 체크아웃
- 기간 내 커밋 필터링 (CommitTimeRevFilter)
- 각 커밋의 diff 추출 (파일 변경 목록)
- 인증 정보 등록 시 자동으로 토큰 복호화하여 사용
- 분석 실패 시 해당 레포만 에러 표시, 나머지는 계속 진행

구현 파일

- `AnalysisRequest.java`, `AnalysisRequestRepository.java`
- `GitAnalyzerService.java`, `GitDiffResult.java`
- `AnalysisService.java`
- `AnalysisController.java`
- `AnalysisCreateRequest.java`, `AnalysisResponse.java`

# 4단계: DB Schema Analyzer 구현 ✅

목표:
DB 구조 변경 감지

분석 대상

- table
- column
- index

방법

앱 DataSource를 사용하여 information_schema 조회 (별도 DB 접속 정보 등록 불필요)

출력

schema evidence (DbSchemaResult)

구현 파일

- `DbSchemaAnalyzerService.java` - information_schema 조회 + 스냅샷 비교
- `DbSchemaResult.java` - 스키마 분석 결과 DTO
- `SchemaSnapshot.java`, `SchemaSnapshotRepository.java` - 스냅샷 저장/조회

변경 파일

- `AnalysisService.java` - DB 스키마 분석 통합, `idProject`로 분석 요청
- `AnalysisCreateRequest.java` - `projectCode` → `idProject`로 변경
- `AnalysisResponse.java` - `projectCode` → `idProject`, `schemaResults` 필드 추가

변경 감지 타입

| changeType | 설명 |
|------------|------|
| TABLE_ADDED | 테이블 추가 |
| TABLE_REMOVED | 테이블 삭제 |
| COLUMN_ADDED | 컬럼 추가 |
| COLUMN_REMOVED | 컬럼 삭제 |
| COLUMN_TYPE_CHANGED | 컬럼 타입 변경 |
| INDEX_ADDED | 인덱스 추가 |
| INDEX_REMOVED | 인덱스 삭제 |

분석 요청 예시

```json
{
  "idProject": "9880d0db-743f-441c-95b9-100c7b7a08b6",
  "startDate": "2026-03-01",
  "endDate": "2026-03-10"
}
```

# 9단계: Change Correlation Engine 구현 ✅

목표

여러 이벤트를 하나의 기능으로 묶기 (correlationKey 기반 그룹핑)

예

schema(테이블 추가) + api(endpoint 추가) → 동일 correlationKey → "기능 변경" 그룹

구현

- correlationKey 기준 그룹핑 (테이블명, API prefix, 디렉토리명)
- 카테고리 조합에 따른 그룹 제목 자동 생성
